The Problem: Every Shipment Type, Every Journey, Every Failure Point

A single feature change in OMS wasn't tested against one flow — it had to hold up across a combinatorial explosion of cases. Shipments could be single-item single-quantity, single-item multi-quantity, multi-item single-quantity, or multi-item multi-quantity. Each of those could move through cancellation, return, or RTO. And at nearly every step — delivery-partner assignment, payment failure, Store OS pickup — the journey could branch again.

Before automation, QA manually walked through this matrix for every release, however small. A minor feature change still meant re-testing dozens of shipment-journey-failure combinations by hand, which made even routine releases slow and made it easy for edge cases to slip through.

What I Built

As a Graduate SDE, I built an automated regression suite covering 100+ test cases across shipment types, order journeys, and failure scenarios, wired into Azure Pipelines so it ran automatically on every merge. Once a run completed, results posted directly to Slack — pass/fail for every case, with the specific shipment ID and order ID where anything failed.

QA's process changed as a result: manual QA didn't start until the automated run had signed off. Since the pipeline already covered the full combination space, QA's time shifted from re-verifying known cases to focusing on what automation couldn't catch.

The Debugging Side-Effect

The Slack alerts did more than flag pass/fail — they pinpointed exactly which step in which journey broke, tied to a real shipment and order ID. That meant a developer could go straight to the logs for that specific ID instead of trying to reproduce a failure from a vague QA report. Debugging time dropped because the pipeline had already done the work of isolating where in the state machine things went wrong.

Why This Felt Like Product Work

Designing the 100+ case test matrix meant deciding which edge cases actually mattered — which combinations of shipment type, journey, and failure point were worth covering, and which were noise. That's a prioritization exercise, not just a testing one. Working through it with QA and developers, figuring out what to automate versus what still needed human judgment, was my first real exposure to thinking like a PM — before I even had an SDE-1 title.

Impact

The pipeline cut manual QA effort by 40% and made release sign-off faster and more reliable across the board. It was recognized with the Fynd Star Award — an annual award given by the Engineering Manager to the top-performing member of the Fynd Commerce Platform team, out of a team of 50, awarded to me while still a Graduate SDE.

The cheapest QA win isn't more testers — it's deciding, deliberately, what a machine should check so people can check what a machine can't.
